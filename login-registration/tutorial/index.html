02 / 先数角色，不急着数机器

先画三方：浏览器、网站后端、Google

你的浏览器显示页面 · 发请求 · 保管 Cookie
Better Auth 网站后端接收登录请求 · 建立本站登录态
Google 的服务确认 Google 账号 · 发放身份凭据

前端网页和登录接口，这次都使用 dash.better-auth.com。但“同一个域名”不证明它们由同一台服务器运行：背后可能有路由、反向代理或多个部署实例。

从这个页面能确认的是角色和公开入口，不能数出真实机器数量。 认证逻辑可以和业务代码一起部署；用了 Better Auth，也不意味着每次登录都必须额外经过一个独立的“Better Auth 公共认证服务器”。

“客户端”有两个语境：对网站后端来说，浏览器是客户端；对 Google OAuth 来说，向它申请登录的 Better Auth 应用是 OAuth client。后者包含网站的服务端逻辑，不只指网页。

一次看完整路线
  1. 浏览器向本站发送“我要用 Google 登录”。
  2. 浏览器前往 Google 授权地址，Google 展示登录界面。本次现场观察到这里。
  3. 用户在 Google 完成身份验证及必要的授权。
  4. Google 让浏览器带着临时 code 回到本站回调地址。
  5. 本站后端检查回调，并向 Google 交换、验证 token。
  6. 本站查找或按配置创建本地账号，建立自己的 session。
  7. 本站通过响应设置登录 Cookie；浏览器按 Cookie 的规则保存、携带。
  8. 下次访问本站，后端验证本站登录凭据，再返回用户数据。
04 / 把网络请求翻译成人话

本次实际看到了什么？

1

先找自己的后端

现场观察POST /api/auth/sign-in/social

请求发往 dash.better-auth.com，记录到 HTTP 200。请求体如下：

{
  "provider": "google",
  "callbackURL": "/"
}

provider 是“选哪家身份服务”；这里的 callbackURL: "/" 是本站登录完成后的落点。它与下面给 Google 的 OAuth 回调地址不同。

2

再前往 Google 的授权入口

现场观察
GET https://accounts.google.com/o/oauth2/v2/auth

地址中有这些参数。下面是从请求记录中整理的字段，不是浏览器 DevTools 的原始截图：

字段实际值 / 已省略的内容用人话读
response_typecode请在完成后给我临时授权码。
redirect_urihttps://dash.better-auth.com/api/auth/callback/google请让浏览器把授权结果带回这个入口。
scopeemail profile openid申请基础身份、邮箱和资料相关范围；没有申请 Gmail 邮件正文或 Google Drive 文件权限。
client_id已省略告诉 Google 是哪个应用来申请；它不是用户身份，也不是 client secret。
state临时值，已隐藏回调时关联、检查这次登录，帮助防止登录请求被冒用或串错。
code_challenge_methodS256使用 PKCE：先交一个校验摘要，换 token 时再证明自己持有对应的 verifier。
code_challenge临时值，已隐藏和本次登录绑定的摘要；它不是 access token。
3

Google 显示登录界面

现场观察GET /v3/signin/identifier → 200

对应前面的 Google 截图。到这里，还没有拿到用户完成授权后返回的 code，更没有观察到换 token 的结果。

05 / 最容易混淆的三个东西

临时兑换券、Google 凭据、本站通行证

临时授权码 code

像一张短期、一次性的兑换券。

标准去向：
Google → 浏览器 → 网站后端。

后端拿它换 token。仅有 code 通常还不够，还需要满足应用认证、redirect URI、PKCE 等校验。

Google 的 token

ID token：带有可验证身份信息的凭据。
Access token：访问已授权 Google API 的凭据。

本例这种后端换码流程：
Google → 网站后端。

二者用途不同；ID token 不能替代 access token 去访问所有 API。Refresh token 是否发放取决于请求和 Google 策略。

本站 session 凭据

像这个网站自己的通行证。

标准去向：
网站后端 → 浏览器 Cookie → 后续本站请求。

它用来登录 Better Auth 网站，不是登录所有 Google 服务的通行证。

为什么需要两层凭据？ Google 的结果帮助本站确认身份；本站仍要管理自己的账号、权限、登录期限和退出状态。之后读取本站数据，通常使用本站 session，而不是每次重新去 Google 登录。

Cookie 是装凭据的载体，不是另一种 Google token

按 Better Auth 文档，常规会话使用 session token Cookie。名称可能出现 better-auth.session_token，HTTPS 环境还可能带安全前缀，也允许自定义。这是文档中的约定，不是我们已确认的网站登录后 Cookie 名称。

收到登录响应

Set-Cookie: [本站会话Cookie]=[隐藏];
HttpOnly; Secure; …

示意，非本网站实测响应。浏览器处理这个响应头；HttpOnly 限制网页 JavaScript 读取该 Cookie。

之后访问本站

Cookie: [本站会话Cookie]=[隐藏]

浏览器按 Domain、Path、SameSite、Secure 等规则，以及请求的凭据模式携带 Cookie。并不是发给所有网站。

所以，浏览器保管的东西，不一定能被网页 JavaScript 读取。Google 域名下的登录 Cookie，也不会因为跳回 Better Auth，就自动变成 Better Auth 的 Cookie。

小检查：登录本站以后，刷新本站页面，通常带什么？

点击一个答案，看看是否分清了这三层。

06 / 你也可以亲手追一次

打开 Network，盯住五个位置

在 Chrome / Edge 中打开登录页，按 macOS 的 ⌘⌥I 或 Windows 的 F12，选择 Network（网络）。工具界面因浏览器版本可能略有差别。

  1. 勾选 Preserve log（保留日志），先选 All。
    否则跳到 Google 后可能看不到前面的请求。只选 Fetch/XHR，会漏掉整页导航的 Document 请求。
  2. 清空列表，再点击 Google 登录。
    搜索 sign-in/social，在 Headers 中看 Request URL / Method，在 Payload 中看 provider 和 callbackURL。
  3. 清掉过滤词，查看 Google 请求。
    找到 /o/oauth2/v2/auth，在 Query String Parameters 中看 redirect_uri、response_type 和 scope。你就知道“找谁、做什么、回来哪里”。
  4. 如果你自己选择完成登录，再看回调请求。
    查找 /api/auth/callback/google，通常会看到 code、state；随后看响应和重定向链上的 Set-Cookie，以及最终落到哪个页面。
  5. 到 Application → Storage → Cookies 查看保存结果。
    看 Cookie 的名称、所属域、HttpOnly、Secure、过期时间。然后刷新网站，观察后续请求是否携带对应 Cookie；可能有单独的 get-session 请求，也可能由页面服务端处理，不能只凭缺少某个接口就判断没登录。
浏览器 Network 看不到网站后端直接向 Google 换 token 的请求。 那段通信没有经过你的浏览器。要确认它，需要网站的后端代码、脱敏日志或服务端追踪；没有在 Network 里看到它，不等于它没有发生。

练习和分享截图时，只保留字段名、域名、路径、状态码，遮住 Cookie、Authorization、code、state 等值。完整 HAR 可能含登录凭据，不要直接公开。

07 / 把请求对应回代码

拿路径找处理函数，比搜 “server” 更有效

以下代码是根据 Better Auth 官方用法和现场请求整理的教学示意，没有声称它就是 dash.better-auth.com 的源文件。

前端：按钮让什么发生

await authClient.signIn.social({
  provider: "google",
  callbackURL: "/"
});

在自己的项目中，先搜 signIn.social、provider: "google" 或按钮文字。再追到创建 authClient 的地方，确认请求的 baseURL。

后端：谁配置 Google

const auth = betterAuth({
  baseURL: process.env.BETTER_AUTH_URL,
  socialProviders: {
    google: {
      clientId: process.env.GOOGLE_CLIENT_ID,
      clientSecret:
        process.env.GOOGLE_CLIENT_SECRET
    }
  }
});

这是服务端配置。Client secret 应留在服务端；然后继续找 auth.handler 或框架适配器，确认谁接收 /api/auth/*。

要追的问题搜索线索追到哪里才算有答案
点按钮后发给谁？signIn.social、createAuthClient、baseURL客户端配置与实际 Request URL 对上。
请求被哪个程序接住？/api/auth、auth.handler、路由适配器找到接入认证逻辑的路由；不必为每个接口找到单独文件，通配路由可能统一处理。
谁拿 code 换 token？Google provider、callback、token endpoint跟进当前依赖版本里的服务端处理，或脱敏服务端追踪。
登录状态存在哪？database、session、secondaryStorage、cookies明确服务端存储与浏览器 Cookie 的分工；不要从文档默认值推断线上配置。
究竟几个服务 / 实例？package.json scripts、Compose、部署配置、代理规则把入口映射到独立部署程序；再看副本数。数据库、缓存、业务服务分开记。
用四句话检查自己是否追明白：
谁拿到什么？发给了谁？存在哪里？下一次请求时谁会用它？
本例可先写成：Google 确认身份 → 后端验证结果 → 本站建立 session → 浏览器以后带本站 Cookie。
