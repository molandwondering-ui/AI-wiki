函数接口让我们可以调用一个功能，而不用了解全部内部实现。但机器仍要处理几个具体问题：去哪执行、参数放在哪、执行完回到哪里、哪些旧值必须保住。**函数调用依靠 call/ret 转移控制流，依靠寄存器和栈传递数据，再依靠保存约定和栈帧维护每次调用的状态。** 递归也使用同样的规则。

本讲的汇编与寄存器约定基于 x86-64 的 **System V AMD64 ABI**，即规定函数如何协作的一套二进制接口规则。Windows x64 使用不同的参数寄存器与栈规则，不能直接照搬本讲表格。

## 一、栈的后进先出结构与函数嵌套自然匹配

设 P 调用 Q。当 Q 正在运行，P 的后续执行暂时挂起；Q 返回后，P 才继续。更早调用 P 的函数，也在等待这条调用链逐层返回。

栈恰好按**后进先出**分配和回收：最后进入的调用先结束。与一次调用相关的栈上状态称为**栈帧**，其中可能包含局部变量、保存的寄存器、栈上传递的参数等。函数并非必须把所有局部量都放在栈上；能留在寄存器里的值通常无需单独开内存。

x86-64 栈通常朝较低地址增长，`%rsp` 指向当前栈顶。减小 `%rsp` 可以腾出栈空间，增大它可以释放对应空间。这里的“释放”主要是让这段地址可被后续栈操作复用，并不意味着系统替每次调用执行一次堆内存分配。

## 二、call 保存继续执行的位置，ret 再把它取回来

视频用 `main` 调用 `multstore` 的反汇编说明：`call` 同时完成两件事：

1. 将 **call 后一条指令的地址**压栈，作为返回地址。
2. 把控制流转到被调用函数的入口。

返回地址不是被调用函数的入口；它是函数执行结束后，调用者应该继续的位置。这个压栈动作由 `call` 自己完成，不需要额外写 `push`。

`ret` 则从当前栈顶取出返回地址，让 `%rip` 所指向的执行位置回到调用者。对于本讲普通的 64 位近调用，返回地址占八字节，`call` 的压栈与 `ret` 的弹栈也相应移动 `%rsp`。

因此，函数在执行 `ret` 前必须把自己分配的栈空间、保存的寄存器等正确恢复，让栈顶重新指向它应当使用的返回地址。

## 三、整数类参数前六个用寄存器，之后用栈

本讲的整数和指针参数按下列顺序传递：

| 参数序号 | 64 位寄存器 | 32 位名称 |
| ---: | --- | --- |
| 1 | `%rdi` | `%edi` |
| 2 | `%rsi` | `%esi` |
| 3 | `%rdx` | `%edx` |
| 4 | `%rcx` | `%ecx` |
| 5 | `%r8` | `%r8d` |
| 6 | `%r9` | `%r9d` |

顺序由调用约定规定，寄存器名称则随访问宽度变化。例如第一个参数是四字节整数时，汇编会使用 `%edi`。浮点参数有另外的分类与传递规则，不能把“六个”当作所有类型的统一上限。

视频中的 `proc` 有八个参数，混合不同大小的整数和指针。前六个经寄存器传递，最后两个放在栈上。

画面代码存在两处排版问题：后三个指针也被写成 `long *`，而后续调用传入的是 `int *`、`short *`、`char *`；更新语句左侧还缺少解引用符 `*`。按后续实参类型及“更新所指对象”的例意校订为：

```c
void proc(long a1, long *a1p,
          int a2, int *a2p,
          short a3, short *a3p,
          char a4, char *a4p) {
    *a1p += a1;
    *a2p += a2;
    *a3p += a3;
    *a4p += a4;
}
```

这不是无关紧要的符号差异：`p += a` 修改指针位置，`*p += a` 才修改指向的数据。此处用小范围输入说明传参，实际使用仍须保证指针有效、类型匹配且运算结果适合相应类型。

本例 `a1`、`a1p`、`a2`、`a2p`、`a3`、`a3p` 依次使用 `%rdi`、`%rsi`、`%edx`、`%rcx`、`%r8w`、`%r9`；后两项 `a4`、`a4p` 使用栈槽。

在被调用函数刚进入、尚未进一步调整栈指针的时刻，布局是：

| 相对入口 `%rsp` 的位置 | 内容 |
| --- | --- |
| `0(%rsp)` | 返回地址 |
| `8(%rsp)` | 第七个参数的栈槽 |
| `16(%rsp)` | 第八个参数的栈槽 |

本例的栈参数槽按八字节安排。即使某个参数值只占一个字节，它也使用一个八字节槽。**这是槽的布局规则，不是把一字节参数的 C 类型变成八字节。** 函数调整 `%rsp` 后，同一对象相对当前栈指针的偏移也会随之改变。

## 四、局部变量需要地址时，栈提供可寻址的对象

视频的 `caller` 初始化 `arg1=534`、`arg2=1057`，调用 `swap(&arg1, &arg2)`，把交换函数的返回值记为 `sum`。之后用交换后的两个对象计算 `diff=arg1-arg2`，最后返回 `sum*diff`。因此局部对象必须拥有可用的内存地址，才能让被调用函数通过指针读写。

![课堂画面：四、局部变量需要地址时，栈提供可寻址的对象](https://github.com/molandwondering-ui/AI-wiki/releases/download/csapp-through-3-10-images/BV19X4y1P7Pn_00289.jpg)

[回看画面 04:49](https://www.bilibili.com/video/BV19X4y1P7Pn/?t=289)

示例汇编先执行 `subq $16, %rsp`，分配十六字节空间；将 534 写入 `(%rsp)`，1057 写入 `8(%rsp)`。`movq %rsp,%rdi` 传入第一个对象地址，`leaq 8(%rsp),%rsi` 传入第二个地址，再执行 `call swap`。返回值位于 `%rax`，随后从栈上重新读取交换后的值，计算差并用 `imulq` 与返回值相乘。最后执行 `addq $16,%rsp`，回收局部空间。

这是画面特定编译结果的布局；手写可独立调用的汇编还需遵守完整 ABI 的调用前栈对齐要求，不能只复制分配字节数。

更复杂的 `call_proc` 先声明 `long x1=1`、`int x2=2`、`short x3=3`、`char x4=4`，再调用：

```c
proc(x1, &x1, x2, &x2, x3, &x3, x4, &x4);
```

四个局部变量分别占八、四、二、一字节，调用时把每个值与它的地址成对传入。调用 `proc` 时，还要另外安排第七、八个参数的传出参数区域。因此，分析栈帧应把“本函数的局部对象”与“为下一次调用准备的参数槽”分开。

## 五、寄存器保存约定明确了谁负责保住旧值

不同函数共享同一组寄存器。P 调用 Q 后，如果 Q 改写了 P 仍需要的寄存器，P 的计算就可能出错。调用约定因此把保存责任分成两类：

| 类别 | 本讲的寄存器 | 责任 |
| --- | --- | --- |
| 调用者保存 | `%rax`、`%rcx`、`%rdx`、`%rsi`、`%rdi`、`%r8`～`%r11` | 调用者若还需要旧值，必须在调用前保留它 |
| 被调用者保存 | `%rbx`、`%rbp`、`%r12`～`%r15` | 被调用函数若改写它，返回前必须恢复旧值 |

画面把 `%rbx`、`%rbp` 等写在 “Caller-saved” 标题下，名称有误；按本讲 System V AMD64 约定，它们属于上表的被调用者保存寄存器。

`%rsp` 单独承担栈指针职责，函数返回时同样必须恢复到正确状态。这里的规定来自 ABI 调用约定，不是处理器自动替程序保存这些通用寄存器。

视频中 P 的参数 `x` 原本位于 `%rdi`，但调用 Q 时 `%rdi` 又要放 Q 的参数。P 因此把 `x` 转存到 `%rbp`，让它跨调用存活。

这同时产生另一项责任：P 改写了被调用者保存寄存器 `%rbp`，所以必须先用 `pushq %rbp` 保存进入 P 时的旧值，返回前再恢复。使用 `%rbx` 同理。保存多个寄存器时，弹出顺序应与压入顺序相反。

这里的 P 同时扮演两种角色：相对 Q，它是调用者；相对调用它的上层函数，它又是被调用者。理解角色关系，就能看懂为什么“把自己的数据存入保存寄存器”之前，还得先保护这个寄存器原来的内容。

## 六、递归的每一层都有自己的待恢复状态

最后的阶乘例子取 $n=3$，调用顺序为 3→2→1，遇到基例后再逐层返回，计算得到 1→2→6。

每层都需要在递归调用结束后继续使用本层的 `n`。视频把 `n` 放在 `%rbx` 中，因此每次进入函数，先把原 `%rbx` 压栈；随后计算 `n-1`，再次调用同一个函数。下一层同样保存 `%rbx`，于是上一层的值就留在了栈上。

当 $n=1$ 进入基例，返回过程开始：每一层取回属于自己的状态，完成乘法，恢复寄存器并返回到自己的调用位置。调用同一个函数并不会共享同一份“本层 n”；共享的是代码，每次调用都有独立的返回地址与待保存状态。

这也解释了递归的成本。较深的调用链会同时保留许多尚未结束的栈帧，持续消耗栈空间；阶乘还会很快超过整数可表示范围。视频提醒，不应仅因为递归写法简洁，就对很大的 n 直接使用这一实现。
