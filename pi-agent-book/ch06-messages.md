# 第6章：消息系统 —— Agent 的记忆如何组织与传递

## 这章在讲什么

Agent（比如 Pi）跟 LLM 对话时，内部存的消息格式和发给 LLM 的格式**不是同一套**。这章讲的就是这两层怎么设计、为什么要分开。

## 核心问题：两套需求打架

你跑了一个命令 `!ls -la`，系统内部想记录：
- 执行的命令是什么
- 输出结果是什么
- 退出码是多少（成功还是失败）

这些结构化数据 UI 要用——比如在终端里把命令输出渲染成好看的代码块。

但 LLM API 只认三种角色：`user`、`assistant`、`toolResult`，而且内容只能是文本。你没法把结构化数据原样塞给 LLM。

**矛盾**：内部要丰富结构，外部要扁平文本。

## 解决方案：两层消息

### 第一层：标准 LLM 消息

就是 LLM API 认识的那三种：

| 类型 | 谁发的 | 包含什么 |
|------|--------|---------|
| UserMessage | 用户 | 文本或图片 |
| AssistantMessage | 模型 | 文本、思考过程、工具调用、token 用量等 |
| ToolResultMessage | 工具执行结果 | 关联到哪个工具调用、执行结果 |

对话就是这三种消息交替出现，直到模型不再要求调用工具。

### 第二层：自定义 Agent 消息

在标准消息之上，Pi 允许应用层注册自己的消息类型。比如 coding-agent 注册了：
- bash 执行记录（命令+输出+退出码）
- 上下文压缩摘要
- 等等

这些自定义消息有三个用途：
1. **UI 渲染**：根据消息类型决定怎么显示（代码块、错误提示等）
2. **持久化**：保存完整结构，重启后能恢复原样
3. **可见性控制**：有些消息只给用户看，不发给 LLM

核心库的自定义消息接口是**空的**——通过 TypeScript 的声明合并（declaration merging），应用层自己往里加类型，核心库不需要知道具体有什么。

## 翻译边界：发给 LLM 之前怎么处理

两步流水线：

```
内部消息 → [transformContext] → [convertToLlm] → 标准 LLM 消息
```

1. **transformContext**：在 agent 消息层面操作——裁剪旧消息、触发压缩。输入输出类型不变
2. **convertToLlm**：跨类型翻译——把所有自定义消息转成标准 UserMessage。结构化字段被拍平成文本

为什么分两步？
- 换上下文管理策略（比如压缩算法）不用动翻译逻辑
- 换应用领域（比如从 coding agent 变成客服 agent）不用重写转换规则
- 换 LLM 供应商不影响 convertToLlm，因为供应商特定的格式化在另一层

## 过滤机制：不是所有消息都该给 LLM 看

有个 `excludeFromContext` 标志，被标记的消息：
- 留在内部上下文里（UI 能显示）
- 但翻译成 LLM 消息时返回 undefined（LLM 看不到）

比如用 `!!` 前缀执行的敏感命令，用户能看到记录，但不会发给模型。

三个可见性层级：
1. LLM 和 UI 都能看到
2. 只有 UI 能看到
3. 持久化保存，但 UI 和 LLM 都看不到

## 对你的启发

这个"两层消息"的设计模式，其实跟你做产品时经常遇到的问题一样：

**内部数据模型 vs 对外展示/接口**

比如 Eden 的语音对话：
- 内部你可能想记录：语音转文字的原文、置信度、时间戳、用户情绪标签...
- 但给 LLM 的只需要：干净的文本内容
- 给 UI 展示的又是另一套：波形动画、文字气泡...

Pi 的做法是：**内部保留完整结构作为唯一真相源，只在边界处做有损翻译**。这样不管下游怎么变（换模型、换 UI、换存储），内部数据不用动。

另一个启发是**可见性控制**——不是所有信息都该暴露给所有消费者。这跟 API 设计里"出参只返回调用方需要的字段"是同一个思路。
