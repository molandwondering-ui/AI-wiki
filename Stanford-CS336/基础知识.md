## 数学基础

### 张量（Tensor）

**多维的数字容器**——按维度组织的数字阵列。标量、向量、矩阵都是张量，张量是统称（就像正方形、长方形都是四边形）：

<div></div>

| 维度 | 名字 | 长什么样 | 例子 |
|------|------|---------|------|
| 0 维 | 标量（scalar） | 一个数 | loss 值 2.31 |
| 1 维 | 向量（vector） | 一列数 | 一个词的 embedding |
| 2 维 | 矩阵（matrix） | 数字表格 | 权重矩阵 W |
| 3 维+ | N 阶张量 | 一摞矩阵 / …… | 一个 batch 的序列 |

在深度学习里它朴素得很：**就是形状（shape）任意的数字数组**，是神经网络中数据流动和运算的唯一载体。

**大模型里什么都是张量**：

```
"hello world" → encode → token IDs [2]（1 维）
             → 查 embedding → [2, 8192]（2 维，每 token 一行）
             → 加 batch → [32, 2, 8192]（3 维）
             → 乘权重 W [8192, 8192] → 过 N 层 Transformer
             → logits [32, 2, 50257]（每位置对词表打分）
```

**shape 和 dtype 是张量的两个基本属性**：

```python
x = torch.randn(32, 2, 8192)  # 形状 [32, 2, 8192]
x.shape                        # torch.Size([32, 2, 8192])
x.dtype                        # torch.float32 / torch.bfloat16
```

调模型代码时 90% 的报错是 shape 对不上（矩阵乘法要求前一个的列数 = 后一个的行数），debug 第一件事就是打印 shape。

**维度惯例（B/S/H）**：`[batch_size, seq_len, hidden_dim]` = [批大小, 序列长度, 隐藏维度]。记住这三个字母，读任何模型代码的 shape 都不迷路。

相关概念：矩阵乘法（GEMM）是张量间运算；算术强度衡量张量搬运 vs 计算；张量并行（TP）= 把大权重张量切块分到多张 GPU。

## 计算与硬件

### 浮点运算（Floating-point Operation）

带小数的数的加减乘除运算。"浮点"指小数点在二进制里是"浮动"的（类似科学计数法）。

深度学习里说"浮点运算"基本就是指矩阵乘法里的乘法和加法。**FLOPs**（Floating-point Operations）= 模型跑一遍总共做了多少次这种运算，用来衡量计算量。

### Kernel（GPU 内核）

跑在 GPU 上的一个函数。CPU 端只是"发号施令"，真正干活的是 GPU 上的 kernel——它定义了每个 GPU 线程具体怎么算、怎么搬数据。

PyTorch 里写 `torch.matmul(A, B)`，底层就是在调一个预写好的矩阵乘法 kernel。可以用 Triton 或 CUDA 写自定义 kernel，针对特定计算优化数据搬运方式，跑得更快。

### HBM（High Bandwidth Memory，高带宽显存）

GPU 专用的片外显存，容量大（如 80GB）但带宽有物理上限（H100 约 3.34 TB/s）。模型权重、激活值、优化器状态都存在这里。

核心瓶颈：计算核心算得飞快，但数据从 HBM 搬过来很慢——所以很多算子不是"算不过来"，而是"数据喂不过来"。

### 算术强度（Arithmetic Intensity）

= 总浮点运算量 ÷ 总显存搬运字节数（FLOP/Byte）

- 算术强度低（如 ReLU = 0.25）→ 内存带宽受限，计算核心闲置等数据
- 算术强度高（如大矩阵乘法 GEMM，N=4096 时 > 1000）→ 计算受限，GPU 满载

H100 的临界点约 295 FLOP/Byte：低于这个值就是内存瓶颈，高于就是算力瓶颈。

### 屋顶线模型（Roofline Model）

一张图看出算子是"算力受限"还是"内存受限"：
- 横轴：算术强度（对数）
- 纵轴：实际性能（对数）
- 左边斜坡 = 内存带宽天花板
- 右边平顶 = 算力天花板
- 拐点 = 临界算术强度（H100 ≈ 295）

### MFU（Model FLOPs Utilization，模型浮点利用率）

= 实际有效算力 ÷ 硬件理论峰值算力

- 50% 左右 = 优秀的分布式训练系统
- 80%+ = 单卡跑大矩阵乘法
- 10% = 系统有严重瓶颈（通信阻塞/小批次/访存墙）

### 算子融合（Operator Fusion）

把多个计算合并成一个 kernel，减少数据在 HBM 和计算核心之间的来回搬运。

比如计算 A + B：不融合 = 读 A → 算 → 写回 → 读 B → 算 → 写回（搬运 4 次）；融合 = 读 A 和 B → 一起算 → 写回一次（搬运 2 次）。

### Tensor Core

GPU 上专门做矩阵乘加的硬件单元，比普通 CUDA Core 快很多。BF16/FP16/FP8 格式的矩阵乘法都走 Tensor Core。

## 数值精度

### BF16（Brain Float 16）

Google 为深度学习定制的 16 位浮点格式：8 位指数（跟 FP32 一样宽，动态范围够大）+ 7 位尾数（精度牺牲一点）。

为什么是大模型训练标准：神经网络对精度噪声鲁棒（梯度本身就有随机性），但对动态范围越界极其脆弱（下溢 → 梯度消失，上溢 → NaN 爆炸）。BF16 保住了范围，砍掉了不需要的精度，显存直接减半。

### 混合精度训练（AMP）

不同部分用不同精度：
- BF16：权重、梯度、激活值（省显存、快）
- FP32：优化器状态（AdamW 的动量和方差需要高精度累积）
- FP32：Softmax、LayerNorm、Loss 计算（涉及指数/除法，低精度会发散）

### 量化（Quantization）

把高精度数值压缩到低精度（如 FP16 → INT8 → FP4），减少显存和带宽占用。

块缩放（Block Scaling）：把张量切成小块（如每 16 个元素），每块共享一个高精度缩放因子，块内用极低精度存相对比例。

## 模型与训练

### Transformer

当前大模型的核心架构。关键组件：
- **自注意力（Self-Attention）**：让序列中每个位置都能"看到"其他所有位置，计算量 O(n²)
- **MLP（多层感知机）**：逐位置的前馈网络，大模型中占 80% 的 FLOPs
- **残差连接 + 归一化**：稳定训练

### 6ND 定律

训练总 FLOPs ≈ 6 × 参数量(N) × Token 数(D)

来源：前向 2ND + 反向 4ND（反向是前向的 2 倍：算输入梯度 + 算权重梯度）。

### 显存开销：12 字节/参数

BF16 + AdamW 全参数训练时：
- 参数：2 字节
- 梯度：2 字节
- 优化器动量 m：4 字节（FP32）
- 优化器方差 v：4 字节（FP32）

8 卡 H100（640GB）理论上限 ≈ 53B 参数，实际 30-40B。

### 梯度累积（Gradient Accumulation）

想要大批次但显存装不下 → 切成小批次串行跑，梯度累加，最后统一更新一次权重。计算量不变，峰值显存降到 1/K。

### 激活检查点（Activation Checkpointing）

前向传播时丢掉中间激活值，反向传播需要时重新算一遍。用时间换空间。最优策略：每隔 √L 层存一个检查点，显存 O(√L)，额外计算 ~20-33%。

### 扩展定律（Scaling Laws）

一组经验公式，描述"投入更多资源，模型能力会怎么变"。把炼模型从炼丹变成了工程：给定预算，用公式算出最优的模型大小和数据配比。

**核心发现**（Kaplan et al. 2020）：测试损失 L 跟三个变量呈平滑的幂律关系（power law，对数坐标上是一条直线）：
- **N**：模型参数量
- **D**：训练数据量（Token 数）
- **C**：训练计算量（FLOPs）

每翻一倍，损失按固定比例下降——可以拿公式算。

**价值：预测而非试错**。大模型训一次几百万美元，没人靠反复试错。工作流：
1. 拿几组小模型跑实验，拟合自己的 scaling law 曲线
2. 用公式外推：给定预算 C，N 和 D 怎么分损失最低
3. 按推算结果直接训大模型，一次押对

（CS336 有专门的 assignment：自己拟合扩展定律，再验证预测准不准。）

**Chinchilla 修正（2022）**：Kaplan 说预算优先砸参数量；DeepMind 纠正为**参数量和 Token 数等比例放大**。经验法则 **D ≈ 20 × N**：
- 7B 模型 → 约 140B Tokens
- 70B 模型 → 约 1.4T Tokens

回头看，GPT-3（175B 参数只喂 300B Token）是严重欠训的——这也是后来 7B 的 Llama 能打过它的原因。

**反直觉推论**：更大不一定更好，配比对了才好。同样预算下，70B 模型喂 300B Token 可能不如 7B 模型喂 300B Token（后者接近饱和，前者欠训）。

**局限**：
- 幂律是平滑下降，预测不了**涌现能力**（emergent abilities）——某些能力过了某个规模突然出现，曲线上看不出来
- 只预测损失/困惑度，不直接预测下游任务——困惑度低 ≠ 数学题做得好
- 数据是有限资源：D ≈ 20N 意味着 70B 模型要吃 1.4T Token，高质量文本快用完了 → 合成数据、多 epoch 训练兴起的原因

### 困惑度（Perplexity）

衡量语言模型预测能力的指标——模型对下一个 Token 越"不确定"，困惑度越高。预训练过程中最可靠的内部评估指标，平滑、单调下降。

## 评估（Evaluation，简称 Eval）

衡量模型到底行不行——给它做题，打分。

### 为什么需要

训练时只能看 loss / perplexity 下降，但这些是**内部指标**：困惑度低只说明"预测下一个 Token 更准了"，不直接等于"数学题做得对"。要回答"模型能力如何"，必须拿具体任务去考。

### 基准测试（Benchmark）——标准化考试

固定题库、固定打分方式，大家用同一套卷子比分数：

<div></div>

| 基准 | 考什么 |
|------|--------|
| MMLU | 57 个学科的多选题（知识广度） |
| HumanEval | 写代码，跑测试用例看通过率 |
| GSM8K | 小学数学应用题 |
| HellaSwag | 常识推理（接下一句） |
| TruthfulQA | 会不会一本正经胡说八道 |

### 人工评估 / LLM 评审——主观题

开放式任务（写作、对话）没有标准答案：
- **人工打分**：贵、慢，但是金标准
- **LLM-as-a-judge**：用更强的模型当裁判打分，便宜快，但有偏好偏差（如偏爱长回答）

### 评估的坑

- **数据污染（Data Contamination）**：考题混进了训练数据，模型是"背过答案"不是真会。基准一旦公开就有此风险
- **基准饱和（Saturation）**：大家都刷到 95%+，卷子就废了，只能出新题
- **刷分（Overfitting to Benchmarks）**：针对特定基准调优，分数涨了但真实能力没涨——应试教育
- **统计噪声**：模型输出有随机性，单次跑分不可靠，要多次采样看方差

### 在训练流程中的位置

```
预训练 → 看 perplexity（内部指标）
    ↓
SFT / RL → 看 benchmark 分数（外部指标）
    ↓
上线前 → 人工评估 + 安全测试（red teaming）
```

业内说法："evals are all you need"——没有靠谱的 eval，连"改动是变好还是变坏"都判断不了。

## 分词（Tokenization）

### Tokenizer 的本质

**字符串 ↔ Token ID（整数）的双向转换器**：

```
encode:  "hello world"  →  [15339, 1917]     （字符串 → 整数序列）
decode:  [15339, 1917]  →  "hello world"     （整数序列 → 字符串）
```

模型从不直接处理字符串——文本进模型前必须 encode 成整数序列，再查 embedding 表变成向量。

结构上就三样东西：
1. **词表（vocab）**：ID ↔ 字符串片段的映射表
2. **合并规则（merges）**：BPE 训练出的合并优先级，决定 encode 怎么切
3. **编解码函数**：encode / decode 两个方向的实现

双向不对称：
- **encode 有确定性但不"唯一"**：同一字符串理论上有多种切法，BPE 贪心规则保证只选一种
- **decode 必须无损**：一个 ID 序列永远还原出同一个字符串，且 `decode(encode(x)) == x` 必须成立

### Token

模型处理文本的最小单元。不是字、不是词，是介于两者之间的"子词片段"。在模型内部就是一个整数 ID。

### BPE（Byte-Pair Encoding）

从 256 个基础字节出发，统计相邻对频次，贪心合并最高频对，迭代扩充词表。常见序列合成一个 Token，罕见序列拆成多个，天然无 UNK。

### 压缩比

= 原始字节数 ÷ Token 数。越大越好（序列越短，注意力 O(n²) 开销越小）。

### 无损往返性（Round-trip Losslessness）

decode(encode(x)) = x，分词器的硬性要求——任何字符串编码再解码必须一字不差。做不到就有致命缺陷。

## 分布式与并行（Distributed Training & Parallelism）

### 模型并行（Model Parallelism / Tensor Parallelism）

模型太大单卡装不下 → 把模型的权重矩阵按列或按行切开，分到多张 GPU 上。每张卡只算一部分，然后通过通信（All-Reduce）把结果拼回来。

- **张量并行（Tensor Parallelism, TP）**：切的是同一层内部的矩阵，卡间通信频繁但延迟低（通常在同一台机器内用 NVLink）
- **流水线并行（Pipeline Parallelism, PP）**：切的是不同层，第 1-10 层在卡 A，第 11-20 层在卡 B。数据像流水线一样依次经过

### 数据并行（Data Parallelism, DP）

每张卡都有完整模型副本，不同卡处理不同数据批次（micro-batch），各自算完梯度后通过 All-Reduce 汇总求平均，再统一更新权重。

- 优点：实现简单，线性扩展
- 缺点：每张卡都要存完整模型，显存浪费

### ZeRO（Zero Redundancy Optimizer）/ FSDP（Fully Sharded Data Parallel）

数据并行的显存优化版。把优化器状态、梯度、参数分片（shard）到多张卡上，每张卡只存 1/N，需要时通过通信临时拿。

- ZeRO Stage 1：只分片优化器状态（省 4 倍）
- ZeRO Stage 2：分片优化器 + 梯度（省 8 倍）
- ZeRO Stage 3 / FSDP：分片优化器 + 梯度 + 参数（省 N 倍，但通信量最大）

### All-Reduce

分布式训练中最核心的集合通信（Collective Communication）操作：所有节点把各自的梯度汇总求和/平均，再把结果广播回所有节点。实现方式通常是 Ring-All-Reduce（节点组成环形，数据沿环传递累加）。

### 通信拓扑（Communication Topology）

- **NVLink**：同一台机器内 GPU 之间的高速互联（H100 约 900 GB/s），延迟极低
- **InfiniBand / Ethernet**：跨机器之间的网络互联（400 Gb/s ≈ 50 GB/s），比 NVLink 慢一个数量级

设计并行策略时：通信频繁的（如张量并行）放同一台机器内走 NVLink，通信少的（如数据并行）可以跨机器。

### 离策略漂移（Off-policy Drift）

在 RL 训练中，推理集群生成 rollout 和训练集群更新权重之间有延迟。如果 worker 太慢，生成的数据对应的已经是"旧策略"，跟当前模型不一致 → 训练不稳定。需要在同策略性（on-policy）和吞吐量之间权衡。

### 梯度同步（Gradient Synchronization）

数据并行中，各卡算完梯度后必须同步（求平均）才能保证所有副本的权重一致。同步是阻塞操作——最慢的那张卡决定整体速度（straggler problem）。

## 推理（Inference）

### 自回归解码（Autoregressive Decoding）

逐 Token 生成：每次只输入一个新 Token，跟全网权重做矩阵-向量乘法（GEMV, General Matrix-Vector Multiplication），算术强度只有 ~1，完全被 HBM 带宽锁死。这是推理慢的根本原因。

### KV Cache（Key-Value Cache）

解码时把之前所有 Token 的 Key 和 Value 缓存下来，避免每次重新计算。用显存换计算。显存占用随序列长度线性增长，是长上下文推理的主要瓶颈。

### 投机解码（Speculative Decoding）

用小模型（draft model）先猜出一串 Token，再用大模型并行验证。猜对了就一次性接受，比逐个生成快得多。本质是把串行的 GEMV 变成并行的 GEMM。

### 预填充（Prefill）vs 解码（Decode）

推理分两个阶段：
- **Prefill**：把整个 prompt 一次性前向传播，构建 KV Cache。类似训练，是计算受限（GEMM）
- **Decode**：逐个生成新 Token，每步只做一个 GEMV。内存带宽受限

### 批处理服务（Batched Serving / Continuous Batching）

推理服务中，不同用户的请求在不同时间到达。系统需要动态地把多个请求打包成批次一起跑（continuous batching），最大化 GPU 利用率。跟训练不同，训练的批次是预先确定的。
